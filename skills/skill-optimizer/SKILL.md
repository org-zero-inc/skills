# Skill Design Reviewer

Skill 设计质量评审工具。**核心信念**：设计质量是语义问题，语义问题需要结构化引导而非自动化规则。

## 评价框架

每个 Skill 从 6 个维度评价，每个维度 🟢 通过 / 🟡 有瑕疵 / 🔴 不通过。

| # | 维度 | 核心问题 | 权重 |
|---|------|---------|------|
| 1 | **结构完整性** | 六层范式零件是否齐全？ | 中 |
| 2 | **可触发性** | LLM 能否正确决定调用此 Skill？ | 高 |
| 3 | **可用性** | LLM 调用后能否顺利完成任务？ | 高 |
| 4 | **安全性** | 是否有不可逆伤害的风险？ | 高 |
| 5 | **内聚性** | 职责是否单一、边界是否清晰？ | 中 |
| 6 | **可维护性** | 后续迭代是否容易？ | 低 |

> **结构完整性 = 零件齐全性，其余 5 维度 = 零件质量**。六层范式是骨架清单，回答「该有的零件有没有」；5 维度是质量标尺，回答「每个零件写得好不好」。两者独立打分，不互相替代。

总评分规则：
- 🟢 **推荐**：全部维度 🟢，或仅有 🟡 `可维护性`
- 🟡 **有风险**：任一「高权重」维度为 🟡，或多个维度 🟡
- 🔴 **不推荐**：任一「高权重」维度为 🔴

## 结构完整性维度（六层范式零件清单）

检查目标 Skill 是否具备六层零件，缺件即 🟡（缺高价值件 🔴），全部齐全 🟢：

| # | 零件 | 检查点 | 价值 |
|---|------|--------|------|
| 1 | 触发边界 | `description` 是否含正向触发词 **和** 负向「不适用」边界 | 高 |
| 2 | 方法论内核 | 是否有思维框架/决策主线，而非纯步骤罗列 | 高 |
| 3 | 确定性锚点 | 精确命令/字段/路径是否硬编码或写查验命令 | 高 |
| 4 | 可判定红线 | 禁止项是否写成可扫描、可拦截的边界（非「注意安全」类废线） | 高 |
| 5 | 质量断言 | 是否有分级验收标准（如 P0/P1/P2 或 🟢/🟡/🔴） | 中 |
| 6 | 正反少样本 | 是否有正例 + 反例（至少各 1，反例不可省） | 中 |

> 缺 1、2、3、4 任一件 → 🔴（骨架残缺）；缺 5 或 6 → 🟡（可用但易漂移）。
> 注意：六层齐全 ≠ 质量高，最终评分仍由 5 个质量维度决定。

## 评审流程

### Round 1: 表面检查

读取目标 Skill 的 `SKILL.md`，检查：

- **YAML frontmatter**：`---` 分隔的头部是否存在？是否包含 `name` 和 `description` 字段？
- **引用文件完整性**：SKILL.md 中引用的 `.py`/`.md`/`.yaml`/`.json`/`.sh`/`.ps1` 文件是否都存在？
- **六层零件齐全性**：按上文「结构完整性维度」清单，逐件核对六层零件是否存在（触发边界、方法论内核、确定性锚点、可判定红线、质量断言、正反少样本）。

若此轮发现 🔴（如缺少 frontmatter、核心文件缺失、或缺 1/2/3/4 任一高价值零件），说明 Skill 有基本结构问题，先提示用户修复再进入深度评审。

### Round 2: 逐维度深入评审

读取 `references/probes/` 下对应的引导问题文件，按维度依次回答（结构完整性维度已在 Round 1 完成快检，本轮不再单独深入）：

| 顺序 | 维度 | 引导文件 |
|------|------|---------|
| 1 | 可触发性 | `references/probes/1-triggerability.md` |
| 2 | 可用性 | `references/probes/2-usability.md` |
| 3 | 安全性 | `references/probes/3-safety.md` |
| 4 | 内聚性 | `references/probes/4-cohesion.md` |
| 5 | 维护性 | `references/probes/5-maintainability.md` |

每分析完一个维度，记录：
- **评级**：🟢 / 🟡 / 🔴
- **发现**：具体问题描述，注明 SKILL.md 中的位置
- **建议**：如何改进

后面维度的分析可以复用前面维度的发现。

### Round 3: 综合判断

汇总 6 个维度的评级，按权重计算总评分。
识别跨维度的交叉问题（例如：职责过宽导致 description 模糊，这是内聚性→可触发性联动）。
输出一句话总体判断。

### Round 4: 输出报告

直接生成以下 Markdown 报告并保存：

```markdown
# 📋 Skill 设计质量评审报告

**Skill**: {skill_name}
**日期**: {date}
**总评**: 🟢 推荐 / 🟡 有风险 / 🔴 不推荐

---

## 逐维度评级

| 维度 | 评级 | 概要 |
|------|------|------|

| 可用性 | 🟡 | ... |
```

## 评审原则

1. **以证据说话**：每个发现必须引用 SKILL.md 的具体段落或文件名，而非笼统判断
2. **承认上下文**：同一个模式在不同 Skill 中意义不同——"5 个步骤"在部署工具中是内聚的，在"工具合集"中可能是职责过宽
3. **可操作性**：每个 🔴/🟡 发现必须附带具体的改进建议，而非只说"不好"
4. **不当裁判当教练**：目标是帮助 Skill 作者发现问题，不是给 Skill 打分排名

## 可判定红线（违反即判定失败）

1. **禁止把「作者有意取舍」判为缺陷** — 只有在取舍导致「触发失败」或「安全/不可逆风险」时才能降级 🔴；否则最多标 🟡 并附「如 X 场景则需补 Y」的条件建议。
2. **禁止凭风格偏好降级** — 命名、排版、文件组织方式只要不影响六层零件与任务完成，不得据此扣分；只描述事实，不评判「好不好看」。
3. **禁止笼统判断** — 每个 🔴/🟡 必须引用具体位置（`SKILL.md:行号` 或文件名）；引用不出的发现不得降级，降为「待观察」。
4. **禁止替代其他 skill 职责** — 本 skill 只评设计质量，不代做创建（skill-creator）、不改动目标 skill、不跑运行时效果评测（evals）。

## 正反少样本

**正例（正确识别「职责过宽」）**

> 某 skill 的 `description` 声称「代码审查 + 自动修复 + 生成测试 + 写文档」四大职责，且正文确实分四套流程。→ 判定：内聚性 🟡，证据 `SKILL.md:3` 描述含四个动词且无统一主线，建议「拆分或声明主职责，其余下沉为可选项」。✅ 证据充分、建议可操作。

**反例（把「有意取舍」误判成缺陷，最常见错误）**

> 某 skill 全部是只读操作（读文件、查日志、生成报告），作者故意省略 HITL 人工确认以追求流畅。评审若按安全性维度给 🔴「缺少人工确认机制，存在不可逆风险」即**错误**。→ 正确判定：无副作用只读 skill 省略 HITL 是合理取舍，安全性 🟢，最多附条件建议「若未来加入写操作，需补 HITL」。

> 记忆口诀：**取舍要有后果才算缺陷；没后果只算偏好。证据要落到位；落不到位就标「待观察」。**
